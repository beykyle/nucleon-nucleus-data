# Notes from EXFOR: cross-check of the corpus against its EXFOR entries

Hand-written summary. The per-entry, per-subentry detail is generated by `scripts/exfor_crosscheck.py` into
`papers/exfor_crosscheck_generated.md` (rerun it after any rebuild). Scope: the 37 EXFOR entries of
`papers/INDEX.md`, i.e. every entry with at least one point resting on reader/digitisation uncertainty. Source: the
local X4 database (release X4-2025-12-31), the same entries the IAEA EXFOR website shows. The website itself (all
IAEA hosts) sits behind a Cloudflare browser challenge and cannot be fetched from scripts; its DOIs were reproduced
from each entry's REFERENCE codes through Crossref instead. 2026-10-08.

## 1. Bibliography and DOIs

- **All 31 entries whose REFERENCE code resolves to a DOI agree with `papers/INDEX.md`.** Each DOI was accepted only
  when the Crossref journal title, volume and first page match the EXFOR code; APS DOIs were constructed and
  checked.
- **No DOI from the REFERENCE code:**
  - F1173 (Izv. Akad. Nauk SSSR; English translation listed by EXFOR as (J,BAS,36,1956,1973)) and O0083 (J. Phys.
    Soc. Jpn. Suppl. 44, conference proceedings) have none.
  - The four J. Phys. G entries O0169, O1103, O1104, O1109 are missed by the code lookup; INDEX's verified DOIs
    stand.
- **Additional sources EXFOR lists**, useful if the journal article lacks the uncertainties:
  - O0169: thesis (T,WASSENAAR,1982);
  - O0580: preliminary reports (C,82KIEV; J,IZV,48,145; C,84ALMAAT; J,IZV,50,157) and an analysis (J,UFZ,32,815);
  - O1199: companion paper (J,PR/C,21,844,1980), data for O-18, N-15, C-12 and Ar-40 (entry O1198);
  - F1173: the English translation (Bull. Acad. Sci. USSR Phys. Ser. 36, 1956 (1973)).

## 2. What the corpus actually uses

- **The corpus reproduces EXFOR exactly.** For every record of these entries, the per-point uncertainty equals one
  EXFOR column, or two in quadrature, at 100 % of points. The exceptions:
  - F0733003 (90Zr(p,p) 25.05 MeV, sm3) is intentionally the authors' 3 % from ERR-ANALYS;
  - one ELM 208Pb set matches at 98 %.
  So the corpus does what the rules say. The problem is the rule's input, not the code.
- **Digitised curves dominate.** 135 of the 142 subentries are STATUS (CURVE), i.e. read off published figures by
  the EXFOR compilers; 7 are (TABLE). Their only per-point uncertainty is often the compiler's data-point reader
  error (0.4–7 %), sometimes alongside author errors where the bars were legible.

## 3. EXFOR relabelled columns between releases (2019–2023)

Several entries were re-labelled, and some re-digitised, by the compilers ("SD:" HISTORY records):
- `DATA-ERR → ERR-DIG` and `ANG-ERR → ANG-ERR-D` (reader uncertainty made explicit): O0079 (2022-10-25),
  O0083 (2019-05-07), O0091 (2022-10-26), O0246/O0253 (2022–2023), O0300 (2023-04-07), O0328 (2023-04-24), and
  others listed in the generated file.
- **Author errors moved with them:**
  - **O0328 (Fricke, 2023-04-24): `ERR-T → ERR-1`, and the data were re-digitised.** ERR-1 is "statistical errors and
    the uncertainty in background subtraction" (001 ERR-ANALYS): the authors' per-point error. The supplement's
    preference rule does not rank `ERR-1`, so every record built from the 2025 database takes `ERR-DIG` (0.4 %)
    instead: sm3/ELM/KDUQ 120Sn(p,p) 40 MeV, CHUQ 59Co/68Zn, and the matching Ay sets. **Fix:** an override naming
    ERR-1 as the author error for O0328, then the fill rule where ERR-1 is blank. The normalisation already matches:
    the ELM/sm3 5.39 % = ERR-2 (2 %) ⊕ ERR-3 (5 %).
  - O0091 (2022-10-26): `ERR-T → DATA-ERR` for at least one subentry. Check the label meanings before trusting the
    preference rule there.
- **Consequence:** which column means "author" vs "reader" depends on the EXFOR release. The supplement's rule
  (ERR-T > DATA-ERR > ERR-S > ERR-DIG) was written against older releases, where `DATA-ERR` was often the *reader*
  uncertainty. Classification must come from each subentry's ERR-ANALYS text, as the audit does, not from the label
  alone. That is now the plan's `classify()` (DATA_CLEANING.md step 2).
